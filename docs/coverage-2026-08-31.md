## The retracted caveat, and what it should have said

This doc claimed the report under-counted everything reachable only through
the app, because gcov flushes on normal exit and every smoke test stops the app
with SIGTERM. **Both halves were wrong**, and checking them cost less than
writing the caveat did.

**The app already exits cleanly on SIGTERM.** `HeadlessMain.cpp:67` and
`main.cpp:1471` install handlers that run an orderly shutdown, and
`headless_smoke.py` has a phase called *"Clean shutdown on SIGTERM"* asserting
exit 0. gcov therefore flushed all along. A handler added in a coverage build
is not merely unnecessary — it is dead code, because those two override it.

**And `Checkpoints.cpp` is not a false positive. It is the finding.** It is the
**no-git fallback**: `checkpoint_create` takes the GitVault path whenever
`ui::CanVersionProject(state)` is true, and only reaches `Checkpoints::Create`
when git is missing (`RemoteProject.cpp:324-338`). Every test machine has git,
so the fallback never runs. The tool reported exactly what is true — 0% of a
path nothing exercises — and it was the reader who supplied a wrong reason.

So the honest reading of the entry is the opposite of the caveat: **the
no-git checkpoint path is untested**, which matters for anyone running without
git, and it is precisely the kind of thing a coverage pass exists to surface.

The lesson is worth more than the entry. A 0%-covered function can mean the
tool is blind, or it can mean the path is genuinely unreached — and the two
look identical in the output. Check which before writing either down.

- Three of the heaviest tests hit their ctest TIMEOUT under `-O0` +

### What is worth reading in it, once the false positives are set aside

A lot of it is destructors, trivial accessors and template instantiations that
gcov counts as separate functions — noise, not gaps. What survives that
filter, and is genuinely worth a look:

- **The no-git checkpoint fallback** (`io/Checkpoints.cpp`, all 8 functions).
  Reached only when `ui::CanVersionProject` is false, which no test machine
  ever is. Either it deserves a test that hides git from the app, or a note
  saying the fallback is accepted as unverified — but not silence.

- **Removal and teardown paths.** `RemoveConfigurationCommand::Execute`/`Undo`,
  `Document::RemoveCamSetup`, `AssemblyDocument::RemoveConfiguration`,
  `SketchFeature::RemoveExternalGeometry`, `GitVault::RemoveRemote`. A
  consistent shape: we test that things can be created and rarely that they can
  be removed, and removal is where dangling references live.
- **`Command::Description()` overloads** for Add/Modify study and feature —
  these are what the History panel and F11's "what changed" print, so a wrong
  one is a version list that misdescribes itself.
- **Availability probes** — `fem::SolverAvailable`, `fem::ModalAvailable`,
  `fem::Available`, `cam::PostExists`, `cam::PostIds`. Cheap to call and each
  one gates a refusal message.
- **`Measure::CheckGeometry`'s lambdas and `NearestPointOn`** — the geometry
  validity check itself, which is the thing an agent is told to trust.
- **`cam::RederiveDepths`** — depths are derived, not typed, and this is the
  function that re-derives them when the model moves under a job.

None of these is a bug on its own. They are the places a bug could sit
indefinitely without any test noticing, which is the whole question this tool
answers.
